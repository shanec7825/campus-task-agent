## 1. 总体思路：码道 Agent Team 承担工程执行，团队三人负责决策与验收

项目从「需求 → 拆解 → 编码 → 测试 → 部署 → 交付物」全流程都在码道内完成，没有使用其他 AI 编码工具。
码道承担的是**工程执行**：按契约拆任务、写代码、跑自检、修回归；团队三人承担**拍板与验收**：定契约、跑验收清单、调业务 Prompt、录屏留痕。

关键做法：

1. **先立契约再写码**。开工前把环境变量、表结构、API 响应体、颜色池、组件 props 全部固化成契约编号（`C-BOOT@1`、`C-DATA@1`、`C-SHELL@1`、`C-AGENT@1` 等），再让 Agent Team 按编号实现，避免多 Agent 并行时互相改坏文件。
2. **写集（write_set）隔离**。每个子任务声明自己独占哪些文件，并行开发时零文件重叠，从流程上消灭「多人抢同一个文件」的冲突。
3. **每阶段人工验收 + 截图留痕**。脚本自检通过 ≠ 验收通过，必须跑起来、亲手点一遍，再把现象交回码道修。

## 2. Agent Team 四角色分工

| Agent | 模型 | 职责 | 本项目中的实际产出 |
|---|---|---|---|
| **领航员（Leader）** | GLM-5.3-Flash | 需求拆解、模块划分、接口与契约定义、任务派发、最终验收把关 | 12 个任务（T1~T12）的拆分与派发、契约表（`2.2.x`）、写集隔离与前置依赖编排 |
| **构造师** | **DeepSeek-V4.1-Flash-1017** | 后端实现：FastAPI 路由、SQLAlchemy 模型、鉴权依赖、双 Agent 调用、SSE hub、APScheduler 催办、积分与知识库 | `backend/app/` 全部模块：7 个路由、8 张表模型、`agents/`、`services/`、`utils/` |
| **画师** | **DeepSeek-V4.1-Flash-1017** | 前端实现：路由与守卫、Pinia store、API 封装、6 个页面、语音块化组件、颜色池联动 | `frontend/src/` 全部模块：`views/`、`stores/`、`api/`、`components/VoiceComposer/`、`composables/` |
| **哨兵** | **DeepSeek-V4.1-Flash-1017** | 代码审查、契约一致性核查、中文分词/JSON 字段读写等易错点排查、阶段对话整理 | 契约一致性检查、`smoke_core.sh` / `smoke_sse.sh` 自检脚本、各阶段 `ai_dialogue/*.md` 的整理（待收尾归档） |

补充说明：

- 码道 Agent Team 的编排方式为「Leader 拆解 → 并行派发给构造师 / 画师 → 哨兵审查 → Leader 汇总验收」；
- 若当前版本不支持为每个成员单独绑定模型，则把 **DeepSeek-V4.1-Flash-1017 设为默认模型**，并在启动 Prompt 中写明各阶段建议模型，由 Leader 在派发任务描述中携带该要求；
- **不设「史官 Agent」**：官方要的是整理后的过程文档而非实时流水，全程旁观的记录型 Agent 只增加 Token 成本。改为**按需史官**——每阶段收尾由持有完整上下文的哨兵一次性整理成 md，存入 `codearts_proof/ai_dialogue/`。

## 3. 各阶段 Prompt 要点

启动指令原文见《校园任务协同AI-Agent-开发方案》第 12 章与 `codearts_proof/prompts/agent_team_启动指令/`（原文归档位）。下表是每阶段 Prompt 的**结构性要点**，也是实际下发给 Leader 的关键约束。

| 阶段 | 下发对象 | Prompt 要点（关键约束） | 验收基准 |
|---|---|---|---|
| 阶段 0 · 骨架搭建 | 领航员 → 构造师 / 画师 | ① 按 2.1.2 目录树建骨架；② 后端 `/api/health` 返回 `{code,msg,data}` 且建 8 张表；③ 前端 6 路由 + Pinia + 颜色池 CSS 变量；④ **`.env` 进 `.gitignore`，只提交 `.env.example`**；⑤ 只搭骨架不写业务 | 前后端可启动、`/api/health` 通、8 张表建表成功 |
| 阶段 1 · 认证 + 任务 CRUD | 构造师 / 画师 | ① 统一响应体 `{code,msg,data}` 与错误码表；② `teacher*→publisher` 等角色规则；③ 任务状态机与 `claim/assign/progress/submit/verify` 全链路；④ 验收通过必须写 `credit_logs` 与通知；⑤ 前端所有请求走 api 层带 `Authorization` | `teacher01` 发布/指派/验收，`student01` 认领/进度/提交，积分与通知到账 |
| 阶段 2 · 双 Agent 闭环 | 构造师 / 画师 | ① LLM 调用必须强制 JSON 输出 + Pydantic 校验失败重试；② 业务 Prompt 逐字复制方案 5.1/5.2（只允许追加 `spans`）；③ **剥离 `style_prompt`，不得混入 details**；④ 歧义进 `unresolved` 逐条提问；⑤ 解析失败/超时 30s 必须友好报错并可重试，不能白屏 | 一句话解析出字段、`措辞严谨` 进 style、出现「下午几点」气泡、产出子任务卡片、二次发布出现相似提示 |
| 阶段 3 · 语音流式 | 画师 / 构造师 | ① `webkitSpeechRecognition`（`continuous` / `interimResults` / `zh-CN`）；② 标点切片阈值写死，`is_final` 顺序正确；③ 停止后延迟 800ms 发送尾句；④ **禁止自动落地**，必须进入悬浮确认态；⑤ 更正（教三→教四）打红问号并覆盖旧值；⑥ 非 Chrome/Edge 禁用语音并提示 | 说一句话后地点被更正为「教四」、块可点开修改、确认后才生成任务、全程无 JS 报错 |
| 阶段 4 · 催办 + SSE + 签到 + 积分 | 构造师 / 画师 | ① APScheduler 三级扫描（warning/urgent/overdue），**同任务同等级去重**；② 逾期扣分只记一条；③ SSE 心跳与断线重连（3 秒）；④ 通知唯一写入口是 `notify_service`；⑤ 签到每任务每人一次 | deadline 设 1 分钟后 1 分钟内红点亮起；签到后发布者收到通知；验收积分与流水对账一致 |
| 阶段 5 · 拆解依赖 + 打磨 | 构造师 / 画师 | ① `depends_on` 前置未完成不可认领（前端置灰 + 后端校验）；② SOP 按步骤清单渲染；③ 全站空/加载/错误态统一 | 前置任务未完成时认领被拒并有可读提示 |
| 阶段 6 · 部署与交付物 | 构造师（部署物）+ 书记官（交付物） | ① 安装脚本幂等（`bash -n` 通过、`.bat` 有 `chcp 65001`）；② README 端口/账号/env 与契约逐项一致；③ 开源组件说明含版本与用途；④ `grep` 无真实 Key；⑤ 留痕三层齐全 | `readme/` 5 个文件 + `codearts_proof/` 三层 + 根 README；干净环境按 README 可复现 |

Prompt 质量的三个共性经验：

1. **给验收条件，而不是只给功能描述**。每条 Prompt 末尾写清「怎么做算通过」，Agent 才能自检；
2. **给禁止项**。例如「禁止自动落地」「禁止 `str.format` 渲染含花括号的 Prompt」「禁止在 `frontend/src` 出现 `MAAS_API_KEY`」，红线写进 Prompt 比事后 review 便宜；
3. **给文件写集**。明确「你只能写这 N 个文件」，是并行多 Agent 不互相破坏的根本原因。

## 4. 排错闭环案例

以下三个案例均为本工程**真实发生并经代码/配置固化**的环境与兼容性问题，现象与处置可在仓库中核验；完整的对话原文与截图请补充到 `codearts_proof/debug/`（模板见 `debug/template.md`）。

### 案例一：Python 3.14 缺少预编译轮子导致后端依赖装不上

| 项 | 内容 |
|---|---|
| **现象** | 在 Python 3.14 环境执行 `pip install -r requirements.txt`，`pydantic-core` / `sqlalchemy` 报「找不到匹配的预编译轮子」，尝试源码编译又缺少 C 编译工具链。 |
| **原因** | 新版本 CPython 发布初期，带 C/Rust 扩展的依赖尚未发布对应 ABI 的 wheel；`pydantic-core`（Rust）与 SQLAlchemy 的 C 加速模块首当其冲。 |
| **让码道怎么修** | ① 不硬改依赖版本去「凑」轮子（会引入不兼容 API）；② 在 `requirements.txt` 顶部写明版本策略与降级指引；③ 安装脚本改为**优先探测 `python3.12` / `python3.11`**，选不到时退回系统解释器并打印 3.14 兼容性风险；④ README 增加 FAQ 与「删除 `.venv` 后重建」的完整步骤。 |
| **结果** | `requirements.txt` 保留宽下限 + 注释说明；`install.sh` / `install.bat` 实现版本探测与风险提示；README Q1 给出可执行修复路径。依赖安装不再依赖用户猜版本。 |

### 案例二：Windows + git-bash 下虚拟环境缺 `Scripts/` 目录

| 项 | 内容 |
|---|---|
| **现象** | Windows 上用 git-bash 执行 `python -m venv backend/.venv`，装完依赖后按 README 执行 `.venv/Scripts/python.exe` 报「文件不存在」，目录里只有 `bin/`。 |
| **原因** | git-bash 的 `python` 解析到了 MSYS2 / mingw 的解释器，该解释器按 POSIX 规则生成 `bin/python` 布局，与 Windows 官方 CPython 的 `Scripts/python.exe` 布局不一致。 |
| **让码道怎么修** | ① 文档明确「统一使用 `.venv/Scripts/python.exe`」，并给出用官方 CPython 绝对路径显式创建 venv 的命令；② `install.sh` 增加 `OS=Windows_NT` 下的解释器路径检测（命中 msys / mingw / `/usr/bin/*` 时提示）；③ 脚本同时兼容探测 `Scripts/python.exe` 与 `bin/python`；④ README 增加 FAQ Q2。 |
| **结果** | 安装脚本在 Windows git-bash 下不再静默产出不可用的 venv；两种布局均能识别，路径歧义被显式提示而非留到启动时报错。 |

### 案例三：APScheduler 4.x 与 3.x API 不兼容导致调度器启动即崩

| 项 | 内容 |
| --- | --- |
| **现象** | 若按 `>=3.10` 的宽约束装到 4.x，`BackgroundScheduler` 的注册/启动方式与代码不匹配，催办调度器启动即抛异常，`lifespan` 启动阶段失败，后端无法提供服务。 |
| **原因** | APScheduler 4.x 重写了调度器与任务注册 API（`add_job` 语义、事件循环绑定方式均变化），与 3.x 不兼容。 |
| **让码道怎么修** | ① `requirements.txt` 显式限制 `apscheduler>=3.10,<4`（唯一收紧主版本的依赖，并在注释中写明理由）；② `lifespan` 中的 `start()` / `shutdown()` 做成可重入、幂等，`RUN_SCHEDULER=0` 时不启动；③ 新增 `backend/scripts/smoke_sse.sh` 覆盖「调度器 start/shutdown 幂等」「三级扫描」「同 now 二次扫描新增 0」「逾期扣分仅 1 行」。 |
| **结果** | 依赖安装稳定落在 3.11.3；`RUN_SCHEDULER=0` 可供自动化验收关闭调度；SSE/催办的自检脚本把这层回归固定下来，避免后续改动悄悄打破。 |

> 案例的共同模式：**先定位环境/版本根因 → 在配置或脚本层做确定性约束 → 用可重跑的脚本固化回归 → 写进文档 FAQ**。这条链路正是官方评分口径中的「AI 原生开发流程覆盖度：需求分析 → 生成 → 测试 → 部署」。

## 6. 体验驱动迭代案例（第二轮 R12~R17）

> 本节记录第二轮「用户实机体验反馈 → 契约 → 任务 → 回归」的完整闭环。素材取自 `codearts_proof/LOG.md`（阶段 7 行）与 `codearts_proof/ai_dialogue/stage7_体验迭代.md`；只写契约与仓库中可核验的事实，未发生的产出与结论不填。

### 6.1 触发：6 条实机反馈不是"优化建议"，而是可复现缺陷

| 反馈 | 用户原话要点 | 性质 |
|---|---|---|
| 1 | AI 模式解析后左侧输入栏被锁定，只能去右侧字段面板改；希望在彩色文字块后继续输入「人数修改为 6 人」并以**增量信息**再解析 | 交互断点：解析即锁死输入，无法追加 |
| 2 | 审核建议不可视化、不可追溯且"死板"；采纳后应以**变色文字块**显示；**不能把建议句塞进数据字段** | 数据正确性缺陷：建议语污染字段 |
| 3 | 右侧手改也应可追溯，自动生成「用户：将 xxx 改为 xxxx」「用户：新建 xxx，内容为 xxxx」 | 可追溯性缺失 |
| 4 | Edge 下按住说话长时间无反应，直到点"结束录音"才一次性出字 | 算法缺陷：无标点时不触发切片 |
| 5 | 学生报名需**老师确认**才生效、可拒绝、审批前可撤回；8 个名额第一个学生报名后第二个报不了 | 模型缺陷：单负责人模型导致名额失效 |
| 6 | AI 交互文档必须按开发方案 md 补齐，不得缺斤少两，也不得编造 | 交付规范缺项 |

其中第 5 条是**结构性缺陷**而非 UI 瑕疵：第一轮 D1「单任务单负责人」把"任务"与"唯一负责人"绑定，`quota` 只被当作展示字段，第 2 名报名的学生必然被"任务已被认领"拦住。用户用不同账号实测复现，成为推翻上一轮决策的直接依据。

### 6.2 反馈如何转成契约（R12~R17 → 6 个冻结契约）

| 反馈 | 需求 | 契约 | 关键约束（可断言） |
|---|---|---|---|
| 1 | R12 增量解析 | `C-AGENT@2` | `ExtractIn{text, base_draft, mode:"incremental"}`；返回合并后的完整草稿 + `changes`；`changes[].old_value` 取 `base_draft`；缺 `base_draft` ⇒ `4001` |
| 2 | R13 建议可视化与分离 | `C-AGENT@2` + `C-TRACE@1` | `new_value` 必须通过 `is_pure_value()`，不合格**丢弃**（宁缺勿污染）；`applied_texts` 与前端文案逐字一致；建议语只进 `ambiguities`/`reason` |
| 3 | R14 手改追溯 | `C-TRACE@1` | `setField` 自动生成 `user_edit` 块；`toTaskPayload` 忽略全部追溯块与 `live` 块 |
| 4 | R15 语音实时 | `C-VOICEUI@2` | `PUNCT_THRESHOLD` 3→1、`MAX_CHUNK_CHARS=12`、`SILENCE_CUT_MS=800`、`onend` 自动续接；`sliceChunk` 6 组样例 |
| 5 | R16 报名审批 / 多名额 | `C-DATA@2` + `C-APPLY@1` | 新表 `task_applications`（`UNIQUE(task_id,user_id)`）；状态机 `pending→approved/rejected/cancelled`；`approved_count < quota` 才可报名；逐成员加分幂等 |
| 6 | R17 留痕补齐 | `C-DELIVERY@2` | 五节结构 `stage7_体验迭代.md`；未发生写「（待人工归档）」；路径必须 `ls` 可验证 |

同时作废两条上一轮规则：D1「单负责人」作废；P1 语音「超过多个标点才切 / 取倒数第二个标点」作废（改为第一个标点即切），函数 `sliceByPunctuation` 更名为 `sliceChunk` 且不留废弃别名。

### 6.3 任务拆分与并发约束（Agent Team 怎么落地）

| 任务 | 角色 | 关键做法 |
|---|---|---|
| T1 | 构造师 | 唯一关键路径起点：建表 + Schema + TS 类型镜像 + 只读聚合服务；`db.py` 只允许追加注释 |
| T2 | 构造师 | 报名/审批全链路 + 多负责人加分 + 签到权限；报名写入只允许在 `applications.py` 一处 |

### 6.4 回归策略（旧用例必须跟着语义改）

1. **语义变更要改旧断言**：`claim` 从"直接占用任务"改为"提交报名申请"，旧 e2e 中"认领后任务变 claimed"的断言必须改成 `apply + approve`。
2. **新增纯值红线断言**：字段值不得出现 `AI建议` / `改为` / `用户：` 前缀；不合格 suggestion 必须让 `changes` 为空。
3. **算法常数用样例锁死**：`sliceChunk` 的 6 组输入输出（含 13 字无标点、单个标点、空串）逐条断言，防止后续再改回旧阈值。
4. **交付物校验扩展**：`verify_delivery.py` 增加本轮留痕项；`ACCEPTANCE.md` 逐条 PASS/FAIL/DEFERRED，DEFERRED 不计 PASS。

### 6.5 这条链路值得写进总结的原因

- **用实测数据推翻自己的上一轮决策**：8 名额 bug 由用户实测复现，比任何设计评审都有说服力；D1 作废、`assignee_id` 降级为兼容字段，是一次"承认设计错并迁移"的完整动作。
- **按真实语速修正算法常数**：阈值 3 → 1 不是拍脑袋，而是"无标点口语永远不触发"的必然结果；配合 12 字强制切与 800ms 静默切，覆盖了"有标点/无标点/停顿"三类真实说话方式。
- **把模型的不稳定输出用确定性校验兜住**：纯值约束 + `is_pure_value()` 丢弃策略，让"模型偶尔把建议句写进字段"不再污染数据；宁可少一条建议，也不脏一个字段。
- **留痕不造假**：本轮留痕分 A/B 段，A 段可立即写（反馈、决策、派工都是已发生事实），B 段必须等真实产出；未发生的统一「（待人工归档）」。
