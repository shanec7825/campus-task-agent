# 开发过程与问题记录规则

> 本文件补充多人接手时的记录分工；长期权限、安全、验证与提交规则仍以 [AGENTS.md](../AGENTS.md) 为准。详细产品计划保存在本地，不复制进过程记录。

## 1. 每类信息只设一个主要位置

| 信息 | 主要位置 | 其他文件如何引用 |
|---|---|---|
| 当前基线、进行中事项、下一步 | [HANDOFF.md](HANDOFF.md) | AGENTS 只给入口，阶段记录保留当时快照 |
| 完整产品规划与建议 | 本地 `.codeartsdoer/plans/ai-workbench/roadmap.md` | 交接写计划路径、版本和状态，不复制整份计划 |
| 当轮需求、契约、任务与验收 | 本地选定阶段 `design.md`、`task.md` | 阶段记录保留必要的脱敏决策摘要与实际结果 |
| 一轮实际开发经过 | `codearts_proof/ai_dialogue/stageN_主题.md` | LOG 用一行链接，不再维护另一份经过 |
| 全部阶段索引 | [LOG.md](../codearts_proof/LOG.md) | 以 stage 编号为身份，不以“第几行”定位 |
| 实际收到的本轮指令 | `codearts_proof/prompts/agent_team_启动指令/` | 标明原文、摘录或摘要；不重建缺失原文 |
| Prompt 改动原因与实测 | `codearts_proof/prompts/prompt迭代记录.md` | 流程 Prompt 与业务 Prompt 分别注明；无改动就不凑编号 |
| 当轮问题总览 | 同一个 stage 文档的问题表 | 正式排错实例用链接引用，不复制多份结论 |
| 真实排错过程 | `codearts_proof/debug/caseN_主题.md` | 复用既有四节模板并更新实例索引 |
| 本轮命令输出与核验报告 | `codearts_proof/reports/` 中脱敏精选副本 | 原始产物留在本地；报告标注来源、命令和未验证范围 |

## 2. 编号如何分配

- **phase / AIW 编号**表示产品路线，不表示实际发生过的工作。本地路线使用 `AIW-00`、`AIW-01` 等标识；它们不能直接当作 stage 编号。
- **stage 编号**表示实际开工的一轮工作。分配前扫描 `LOG.md` 与 `ai_dialogue/stage*.md` 的最大已用编号，取下一号；不补历史缺号，不重用被取消或回退阶段的编号，不按行数计数。
- **P-编号**表示真实 Prompt 演进记录。另行扫描现有表；流程调整不冒充业务模型效果。没有业务 Prompt 变更时，不修改 `backend/app/agents/prompts.py`。
- **问题编号**采用 `S<stage>-I<两位序号>`，例如本轮 `S17-I01`；后续继续发生同一问题时沿用原编号，并链接新证据。
- **debug case 编号**沿用现有模板与索引的下一号。只有实际排错需要完整记录时才创建，文档澄清、未复现风险和未来功能缺口不强行冒充已修复 Bug。
- 截至本次整理，本轮登记为 stage17 / P-017；其余编号以开工时实际文件为准，不永久固定“下一阶段”。

## 3. 一轮工作的记录顺序

1. 开工时记录本轮授权、基线 SHA、既有工作区差异、目标和非目标；选定一个 stage 文档，开工状态先写“进行中”。
2. 说明本轮 `design.md` 与 `task.md` 的路径、版本或状态；计划改变时写原因，不将新计划冒充原始指令。
3. 记录实际平台、工具、模型可核验程度与实际派工。未调用子 Agent 就写未调用；没有独立审查能力则据实说明。
4. 问题出现时登记现象、复现或证据、原因判定状态、处理动作和结果；不要等收尾后凭印象补齐失败过程。
5. 执行验证后再填命令、工作目录、环境、退出码、计数与报告。历史结果、mock、模拟视口、真机、真实模型和 CI 分开标注。
6. 收尾更新同一 stage 文档、LOG 同一行与 HANDOFF。提交和 CI 只有实际发生后再补；未发生写“未执行”或“待验证”。

状态使用“进行中 / 本地完成 / 已提交 / 已推送 / CI 通过或失败 / 已部署 / 已回退 / 已取消 / 待验证”。这些状态分别描述真实事实，不因“本地完成”自动推导其他状态。

## 4. 回退、旧记录和问题如何避免混淆

- 代码当前事实用 Git 与实际行为核对；HANDOFF 汇总目前状态；历史阶段只证明当时发生的事情。发现冲突先写核对结论，不以任何单份文档替代事实检查。
- 回退后用新阶段或当前阶段补充说明：原起点、目标基线、用户说明、实际核对和受影响内容。本轮未知的回退命令、执行时间、原因不得猜测。
- 原有阶段的通过、失败、未完成和工具归属保持原文。更正时追加注明依据的说明，不把旧失败覆盖为成功。
- 只有讨论或已丢弃的未提交工作，不追溯编造“已完成阶段”和测试结果。本次旧 `phase3-activity-workflow` 接手路径已失效，相关说明见 stage17。
- 新增功能缺口写进待办；源码可疑点写“待复现”；已证实的错误写问题单；验证通过后才写“已修复”。
- 同一问题由一个记录条目汇总最终状态；其他阶段用问题编号和证据链接引用，不各写一套互相冲突的结论。

## 5. 多 Agent 写入与交接

- 同一轮只指定一个记录负责人维护 LOG、HANDOFF、Prompt 索引和同一个 stage 文档。其他 Agent 提供证据，由该负责人合并；不用多个 Agent 同时改总索引。
- 并行写代码遵守独立 worktree 和文件归属要求。普通分支不能隔离同一目录的文件写入；只读审查可共享工作区。
- 切换 Agent 前确认原写入者已经停止或已隔离。新 Agent 先检查 Git 差异，不覆盖未归属内容。
- 编号分配由记录负责人串行完成；若发现重号，先查已存在的记录并合并身份或另分新号，不删除原始证据。

## 6. 本地计划与远端材料

详细计划留在 `.codeartsdoer/plans/`，无需为了开发把它上传。Git 忽略只意味着不会正常提交，不等于远端备份。切换 worktree、机器或云端时核对文件；缺失则先补齐依据。

AGENTS、HANDOFF、记录规则和实际脱敏过程记录可作为仓库候选文档，但本轮没有提交推送。未来获得推送授权时，仍逐项检查实际暂存清单；不整目录强制提交计划、原始日志、凭证或数据库。

这套约定用于约束接手流程，无法保证任何工具都会自动执行所有要求。需要核对时运行本轮实际的链接、编号和 Git 边界检查；业务变化仍依靠已有行为测试与独立审查。
